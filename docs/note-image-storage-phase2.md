# 第二階段：記事圖片獨立儲存與備份

## 已建立的遠端備份錨點

在修改前，已從 `main` 建立不合併的唯讀用途分支：
`backup/issues-before-image-storage-2026-10-28`。

此分支保留當時的 `issues.json`（blob SHA `95457e9191edf9aed2fb3361dbcb93fb959e7cfa`），包含當時已同步的文字與內嵌圖片。**不要刪除此分支。** 這不是使用者裝置尚未同步資料的備份。

## 上線前的本機備份步驟

1. 在原本編輯記事的每一個裝置檢查 GitHub 同步狀態，先處理「本機編輯尚未上傳」。
2. 確認 `issues.json` 已包含預期的文章，再從 GitHub 下載一份 JSON 保存到裝置。
3. 不要清除瀏覽器或 PWA 的本機資料與權杖，直到跨裝置驗證完成。

## 本 PR 的範圍

- 新增或編輯記事時，**新貼上的 Base64 圖片**先以 GitHub Contents API 上傳到 `media/entry-images/<uuid>.jpg`，再在記事 JSON 中保存公開的 `raw.githubusercontent.com` 圖片 URL。
- 既有 Base64 圖片不會批次改寫；只有當該篇記事重新儲存時才逐張轉移。
- 既有圖片 URL 原樣保留；文字和表格原有處理方式不變。
- 上傳失敗會阻止儲存記事，避免產生指向不存在圖片的文章。
- 目前仍保留整份記事資料約 850,000 bytes 的防護門檻，以及每篇最多三張附圖的編輯限制。
- 圖片上傳成功但後續記事儲存失敗，可能留下未被引用的圖片檔案；日後需設計清理工具。

## 安全與限制

圖片上傳到**公開** Repository，任何知道圖片網址的人都能讀取；不適合私人圖片。GitHub token 僅由瀏覽器直接傳送 GitHub API，不寫入文章資料。圖片會成為 Git 版本歷史的一部分，刪除檔案不會自動清除歷史。圖片容量、GitHub API 頻率和 Repository 大小仍受 GitHub 規範限制，不能視為無限圖片空間。

## 合併前手動測試

1. 確認備份分支與 `issues.json` 可正常讀取。
2. iPad Safari / PWA：新增文章 + 一張照片，儲存後確認 `issues.json` 只有 URL、`media/entry-images` 有圖片。
3. 重新載入、跨裝置同步，確認圖片可正常顯示。
4. 編輯舊有 Base64 圖片記事並儲存，確認內容不變且圖片仍可顯示。
5. 無權杖、失效權杖、網路中斷時，確認顯示錯誤且舊記事不丟失。
6. 跨裝置同步衝突與接近 850 KB 時，確認仍能保留本機草稿。

本 PR 未經真實 iPad 瀏覽器端到端測試，不應直接合併正式站。
